# 設計判断まとめ

このドキュメントは、このアプリを作る過程で行った技術的な意思決定とその理由を、開発の過程に沿ってまとめたもの。
コードを読まなくても「何を・なぜそう作ったか」が短時間で伝わるように、ES・面接・技術記事の下敷きとして使える形で書いている。

## なぜこのアプリを作ったか

就活生・エンジニア未経験者向けに、技術記事URLを「要約」「メリット・懸念点」「今後の展望」「用語解説」に変換する
学習アプリ。ただの記事まとめアプリで終わらせないために、「他のアプリにはない実利用価値」を常に基準に機能を選んだ
（詳細は下記「二番煎じにしないための機能設計」）。

## コスト設計: BYOK（Bring Your Own Key）と運営者キーの使い分け

Gemini APIの無料枠だけで運用を続けるために、コスト負担者を「誰のためのAI呼び出しか」で明確に分けた。

- **BYOK（ユーザー自身のキー）**: URL手動要約・模擬面接AI・3分ハンズオン・AIエディタ設定エクスポートなど、
  「そのユーザー個人が能動的にトリガーする生成」はすべてBYOK。ブラウザの`localStorage`にのみキーを保存し、
  リクエストごとに`x-gemini-api-key`ヘッダーでサーバーへ渡すだけでDBには一切保存しない設計（`src/lib/apiKeyStorage.ts`）。
  他人にアプリを公開しても、持ち込んだURLの要約コストは各利用者自身のGemini無料枠に紐づく。
- **運営者キー（共有コンテンツ）**: 注目ピックアップの自動要約・AIツールピックアップ・音声ポッドキャスト・
  技術論争サマライザーなど、「1回生成すれば全員が使い回せる」ものは運営者の`GEMINI_API_KEY`を使う。
  クロール時点でエンゲージメント上位のみ（`FEATURED_MAX_TOTAL = 6`件/サイクル）に絞ることで、
  無料枠を使い切らない設計にしている（`src/lib/crawlers/refresh.ts`）。

この線引きを最初に決めておいたことで、新機能を追加するたびに「これはBYOKか運営者キーか」を機械的に判断できた
（例: ポッドキャストは「1日1本を全員で聴く」ので運営者キー、ハンズオンコード生成は「その人が読んでいる記事」なのでBYOK）。

## 本番障害: Postgresの接続プール枯渇

**何が起きたか**: SQLiteでのMVP開発からSupabase Postgresへ本番移行した直後、`refreshFeed()`が新規記事を
`Promise.all`で一括作成する際に、Supabaseのプールド接続（pgbouncer）を使い切り、書き込みがタイムアウトした。

**なぜローカルで気づけなかったか**: SQLiteには接続数の上限という概念がなく、100件以上の同時書き込みも問題なく
通っていた。Postgresに切り替えて初めて顕在化する、環境差に起因するバグだった。

**修正**: `src/lib/crawlers/refresh.ts`に`mapWithConcurrency()`（同時実行数を制限して`fn`を実行するヘルパー、
デフォルト`DB_WRITE_CONCURRENCY = 3`）を実装し、`Promise.all`での一括発火をやめた。本番で336件の記事作成が
成功することを確認して修正完了とした。

**再発防止**: このセッションの後半で`load-tests/`に負荷テストを追加し、接続プールに負荷がかかる読み取り／
キャッシュ経路（`GET /api/feed`・キャッシュヒット時の`POST /api/summarize`）を検証した
（詳細は[../load-tests/README.md](../load-tests/README.md)）。書き込みバッチ処理そのものは外部クロール先への
迷惑・Gemini無料枠浪費を避けるため繰り返し負荷テストの対象外とし、コードレビューと本番実績（336件成功）で
担保している。

## スケジューラ設計: Vercel CronとGitHub Actionsの使い分け

Vercel Hobbyプランはcronの実行頻度が1日1回までに制限されている。一方フィード更新は3時間おきに回したい。
この制約に対して、頻度で使い分ける設計にした:

- **`vercel.json`（Vercel Cron）**: 週次のAIツールピックアップ更新・週次ダイジェスト送信など、1日1回以下で
  十分なジョブ。`CRON_SECRET`という名前の環境変数を設定すると、Vercelが自動で`Authorization: Bearer $CRON_SECRET`
  ヘッダーを付けてくれる。
- **`.github/workflows/cron-refresh.yml`（GitHub Actions）**: 3時間おきのフィード更新・毎日6時JSTのポッドキャスト
  生成など、Vercel Hobbyでは表現できない頻度のジョブ。`x-cron-secret`ヘッダーで同じ`CRON_SECRET`を使い回している。

両方から同じエンドポイントが叩かれても壊れないよう、`POST /api/feed/refresh`は`urlHash`のユニーク制約で、
`POST /api/tools/refresh`はupsertで、それぞれ冪等に設計してある。

## Next.js 16の破壊的変更に注意しながら開発した経験

このプロジェクトは「学習済みの知識が通用しない前提で読む」ことを明示的に要求される環境だった
（`AGENTS.md`に「This is NOT the Next.js you know」という注記がある）。実際に踏んだ・事前に踏まないよう対策した変更:

- **`params`がPromiseに変更**: 動的ルートセグメント・Route Handler・`generateMetadata`・`opengraph-image.tsx`
  すべてで`params: Promise<{...}>`になった。`src/app/u/[slug]/opengraph-image.tsx`で同期的な`{ slug: string }`
  のまま実装してしまい、本番で全リクエストが500エラーになるバグを実際に出した。原因はドキュメントのバージョン
  履歴（「v16.0.0: params is now a promise」）を読んで特定し、`await params`に修正、本番で200に戻ることを確認。
- **エラーバウンダリのprops変更**: `error.tsx`/`global-error.tsx`が受け取るのは`reset: () => void`ではなく
  `unstable_retry: () => void`。これは実装前にドキュメントを確認して事前に気づき、誤実装を防げたケース。

「本番で実際にバグを出した箇所」と「事前にドキュメントを読んで防げた箇所」の両方があるのは、
学習済み知識と現在のAPIのズレにどう向き合うかという、AI協働開発ならではの経験として語れる部分。

## iOS PWA対応で踏んだハマりどころ

- **黒背景バグ**: `viewport`に`viewportFit: "cover"`を設定していなかったため、iOSの`env(safe-area-inset-*)`が
  解決されず、かつ`prefers-color-scheme: dark`に応じて`--background`を暗転させるCSSがあったため、セーフエリア外が
  ほぼ黒く表示される不具合があった。このアプリは全コンポーネントがライトテーマ固定でダークモード対応をしていない
  ため、ダークモード時の背景色反転自体を削除して解決。
- **セッションCookieが本番で効かない**: `next start`は`NODE_ENV=production`を設定するため、Cookieの`Secure`
  フラグを`NODE_ENV`から判定するとHTTP環境で常にCookieが落ちる。実際のリクエストプロトコル
  （`x-forwarded-proto`ヘッダー）から判定するよう修正。
- **左右スワイプと横スクロールUIの衝突**: タブ切り替え用の左右スワイプジェスチャーを実装していたが、フィードの
  日付チップ列・AIツールのカテゴリチップ列（意図的に横スクロールできるUI）をドラッグする操作と衝突し、
  誤ってタブが切り替わる問題が発生。最終的にスワイプでのタブ切り替え自体を廃止（タップのみに統一）して解決。
  さらに、この横スクロールUIのバウンス（弾む動き）が画面全体に伝播し、フィード画面自体が左右にドラッグできて
  しまう副作用もあった。`html`/`body`に`overflow-x: hidden` + `overscroll-behavior-x: none`を追加して解決。

## 二番煎じにしないための機能設計

単なる「記事まとめ＋AI要約」アプリで終わらせないために、他のニュースアプリ・学習アプリと役割が被らない機能を
優先して実装した:

- **技術論争サマライザー**: 記事単体の要約ではなく、Hacker Newsのコメント欄の実際の温度感（賛成派/懸念派）を
  AIが構造化。X APIは有料のため対象外、Hacker News（既にクロール済み・無料の公開API）に絞ってスコープを縮小した。
- **リポジトリチェック**: 一般的な「破壊的変更ニュース」の一覧ではなく、ユーザーが指定した公開リポジトリの
  実際の依存関係とキーワード照合し、「自分に関係あるものだけ」を返す。Gemini APIを一切呼ばない決定的な
  キーワード照合のため、何度でも無料で実行できる設計。
- **音声ポッドキャスト**: 移動中でもキャッチアップできる、というアプリの利用シーン自体を広げる機能。
  Geminiのマルチスピーカーテキスト読み上げ（TTS）で2人の掛け合い形式の音声を生成し、Vercel Blobでホスト。
- **AIエディタ設定エクスポート**: 技術記事を読んで終わりにせず、そのままClaude Code/Cursor向けの設定ファイルとして
  自分の開発環境に持ち込める。このアプリ自身のユーザー層（Claude Code/Cursorを使う開発者）と直接噛み合う設計。

いずれも「実装コストと実際の利用価値を天秤にかけて機能を絞る」判断を繰り返した結果で、Geminiが提案した
アイデア（例: 論文の動く図解ジェネレーター）はハルシネーションリスク・XSSリスクの割に価値が見合わないと判断し
見送るなど、「思いついた機能を全部実装する」のではなく取捨選択している。

## 品質保証: テスト・CI・セキュリティ・負荷テスト

開発の後半で、それまで手動（`tsc`/`eslint`/`build`を都度手で実行、本番DBに対する`curl`での動作確認）に頼っていた
検証プロセスを自動化・体系化した:

- **テスト**（[../README.md#テストci](../README.md)）: DB接続不要な純粋関数を中心にvitestで単体テスト。
  実際に見つけた2つのバグ（`@eslint/js`のスコープ除去が`"js"`という汎用的すぎるキーワードになり
  `"Next.js"`を含む記事に誤マッチしていた問題、HTMLエンティティ`&#x27;`の未デコード）は、修正だけでなく
  再発防止テストとして残している。
- **CI**（`.github/workflows/ci.yml`）: push/PRごとに型チェック・Lint・テスト・ビルドを自動実行。
- **セキュリティ監査**: `pnpm audit`で見つかった8件中6件を修正、残り2件（`brace-expansion`）はESLintの
  依存関係を壊すことが判明したため、実際に攻撃者が到達できない経路であることを確認した上でリスク受容とした
  （詳細は[../README.md#セキュリティ](../README.md)）。「脆弱性を機械的に全部潰す」のではなく、
  実際の攻撃可能性とツールを壊すリスクを天秤にかけて判断した例。
- **負荷テスト**: 上記「本番障害」の節を参照。
