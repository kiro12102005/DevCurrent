# 負荷テスト

## 背景（実際に起きた障害）

本番デプロイ後、`refreshFeed()`（Qiita/Zenn/Hacker News/ArXivを並列クロールし、新規記事を一括作成する処理）が
Supabaseのプールド接続（pgbouncer）を使い切り、書き込みがタイムアウトする障害が発生した。ローカル開発ではSQLiteを
使っていたため接続数の上限が存在せず、この問題は本番でPostgresに切り替えて初めて顕在化した。

原因は`refreshFeed()`内で100件以上の新規記事作成を`Promise.all`で一度に発火していたこと。
`src/lib/crawlers/refresh.ts`の`mapWithConcurrency()`（同時実行数3に制限するヘルパー）を実装して修正し、
本番で336件の記事作成が成功することを確認済み（詳細は[../docs/DESIGN_DECISIONS.md](../docs/DESIGN_DECISIONS.md)）。

## この負荷テストで検証すること

`mapWithConcurrency`が実際に効いている書き込みパス（クロール時のバッチ作成）は、外部クロール先（Qiita/Zenn/HN/ArXiv
の実API）と場合によってはGemini APIの実呼び出しを伴うため、繰り返し負荷テストするのは現実的ではない
（外部APIへの迷惑・Gemini無料枠の浪費）。そのため本テストは範囲を絞り、**ローカルサーバーに対してのみ**、
Postgres接続プールに実際に負荷がかかる2つの読み取り／キャッシュ経路を検証する:

1. `GET /api/feed` — 1リクエストで最大5クエリ（注目ピックアップ3ソース分＋通常一覧＋件数）が同時に発火する、
   読み取り経路の中で最もクエリ数が多いエンドポイント。
2. `POST /api/summarize`（キャッシュ済みURL） — キャッシュヒット時は1クエリ程度で返る軽量な経路。
   **必ず既にキャッシュされたURLに対してのみ実行する**ようスクリプト内で担保しており、Gemini APIの新規呼び出しは発生しない。

k6を検討したが、このdevcontainerにはapt経由でインストールできなかったため、Node製の
[autocannon](https://github.com/mcollina/autocannon)を採用（プロジェクトのツールチェーン内で完結し、追加のシステムパッケージが不要）。

## 実行方法

```bash
pnpm build && pnpm start   # 別ターミナルでローカルサーバーを起動
pnpm load-test              # このディレクトリのスクリプトを実行
```

`load-tests/feed-load-test.mjs`は`localhost`/`127.0.0.1`以外のホストへのリクエストを起動時に拒否する
セーフガードを持つ（本番を誤って負荷テストしてしまう事故を防止）。

## 結果（20同時接続・15秒、本番と同じSupabase Postgresに接続したローカルサーバーに対して実行）

| エンドポイント | 平均レイテンシ | p99レイテンシ | 平均req/s | エラー数 |
|---|---|---|---|---|
| `GET /api/feed` | 1634ms | 2257ms | 12 | 0 |
| `POST /api/summarize`（キャッシュ済み） | 319ms | 410ms | 62 | 0 |

**エラー・タイムアウトはゼロ**（`errors: 0, timeouts: 0, non2xx: 0`を明示的に確認済み）— 20同時接続程度では
接続プールが枯渇するような事態は再現しなかった。

**分かったこと**: `/api/feed`は`/api/summarize`（キャッシュヒット時）と比べてレイテンシが約5倍・スループットが
約1/5。原因はクエリ数の差で、`/api/feed`は1リクエストあたり最大5クエリ（`Promise.all`で3ソース分の注目ピック
アップ＋通常一覧＋件数）を発火するのに対し、`/api/summarize`のキャッシュヒット経路はほぼ1クエリで完結する。
20同時接続なら実用上問題ないレベルだが、フィード画面はこのアプリで最もアクセス頻度の高い画面でもあるため、
将来的にアクセス数が伸びた場合は3ソース分のクエリを1つのwindow関数クエリにまとめるなどの最適化余地がある
（現時点では未実施・優先度低と判断）。
